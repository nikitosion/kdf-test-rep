# Сценарий занятия «Инженерный контур»

Общая демонстрация занимает 50–65 минут. Оставшиеся 25–40 минут 90-минутной пары — начало добровольной самостоятельной работы. Студенты уже могут запускать Kotlin в IDE.

Цель: показать цикл «требование → тест → ошибка → исправление → автоматическая проверка». На занятии разбираем только `displayName`; `canSendMessage` студенты исследуют самостоятельно.

## Что открыть перед занятием

- Локальный демонстрационный проект: `D:\Code Projects\Kotlin\kfd-engineering-loop-practice-demo`.
- Вкладку Actions студенческого шаблона для показа готового запуска. Демонстрационный проект по решению преподавателя остаётся локальным и не имеет remote.
- [Студенческий шаблон](https://github.com/nikitosion/kfd-engineering-loop-practice).
- [Задание в Academy](https://academy.mephi.ru/edu/lesson/8add1ee5-e351-4bed-a546-f3b7be8108b2). Занятие оставлено закрытым по просьбе преподавателя; откройте его в нужный момент.

Начальное состояние демонстрации: одна функция, один тест, только Assemble в CI. Студенческий шаблон начинается с готовой базы: обработка null, два теста, Assemble и Test.

Тег `lesson-start` отмечает исходное состояние локальной демонстрации. Для повторной репетиции создавайте отдельный клон с этого тега, чтобы не стирать свою работу. Эталон и файл `teacher-solutions.md` предназначены только преподавателю; публикуйте разбор после самостоятельной работы.

## 1. Структура проекта — 5–10 минут

Покажите `app/src/main/kotlin/kfd/DisplayName.kt`, `app/src/test/kotlin/kfd/DisplayNameTest.kt`, `.github/workflows/ci.yml` и Wrapper.

Объясните: основной код реализует поведение; тест описывает конкретное ожидание; workflow поручает GitHub выполнить команды. `assemble` собирает основной код, `test` компилирует и запускает тесты, `build` включает сборку и проверки.

Вопрос группе: «Достаточно ли успешной компиляции, чтобы функция делала то, что нам нужно?»

## 2. Один зелёный тест — 10 минут

Исходная функция:

```kotlin
package kfd

fun displayName(name: String?): String = name.toString()
```

Исходный тест:

```kotlin
package kfd

import org.junit.jupiter.api.Assertions.assertEquals
import org.junit.jupiter.api.Test

class DisplayNameTest {
    @Test
    fun preservesName() {
        assertEquals("Анна", displayName("Анна"))
    }
}
```

Спросите: «Какой именно пример подтверждает этот тест? Проверяет ли он все разрешённые аргументы?»

Запустите весь класс стрелкой в IDEA. Ожидается один успешный тест. Покажите ожидаемое значение первым аргументом `assertEquals`, а результат функции — вторым.

Те же проверки в терминале IDEA из корня проекта:

```powershell
.\gradlew.bat assemble
.\gradlew.bat test --rerun-tasks
```

В Bash используйте `bash ./gradlew assemble` и `bash ./gradlew test --rerun-tasks`.

## 3. Новое требование и падающий тест — 10 минут

Сформулируйте: «Если имя не передано, показываем Гость».

Спросите: «Что сейчас вернёт функция? Как записать наше ожидание?» Добавьте в существующий класс:

```kotlin
    @Test
    fun handlesNull() {
        assertEquals("Гость", displayName(null))
    }
```

Запустите весь класс. Получится два теста, один падает: ожидали `Гость`, получили строку `null`. Покажите имя теста, ожидаемое и фактическое значения.

## 4. Что поручено CI — 10–15 минут

Текущая подготовка: демонстрационный репозиторий остаётся локальным. Покажите разницу командами assemble и test в терминале, затем откройте успешный запуск студенческого шаблона и его workflow. Описанная ниже живая отправка демонстрационных изменений возможна только после отдельного подключения удалённого репозитория; сейчас git push в демонстрации выполнять не нужно.

В исходном workflow после Checkout и Set up Java есть только:

```yaml
      - name: Assemble
        run: bash ./gradlew assemble --no-daemon
```

Отправьте новое требование:

```bash
git add app/src/test/kotlin/kfd/DisplayNameTest.kt
git commit -m "Add missing name requirement"
git push
```

В GitHub откройте Actions → запуск для нового коммита → check → Assemble. CI зелёный.

Спросите: «Почему локальный тест падает, а GitHub показывает успех? Что мы поручили ему выполнить?»

Добавьте после Assemble на том же уровне отступов:

```yaml
      - name: Test
        run: bash ./gradlew test --no-daemon
```

```bash
git add .github/workflows/ci.yml
git commit -m "Run tests in CI"
git push
```

Покажите красный шаг Test и тот же текст ошибки. Ошибка обнаружилась без изменения функции — потому что появилась нужная проверка.

## 5. Исправление и зелёный результат — 10 минут

Спросите: «Как вернуть запасное значение, если имя отсутствует? Что мы разбирали на прошлом занятии?»

Итоговый код:

```kotlin
package kfd

fun displayName(name: String?): String = name ?: "Гость"
```

Запустите весь класс: два успешных теста. В локальной демонстрации сохраните исправление коммитом. Команду push ниже выполняйте только если отдельно подключите удалённый репозиторий:

```bash
git add app/src/main/kotlin/kfd/DisplayName.kt
git commit -m "Handle missing name"
git push
```

Покажите успешные локальные проверки и готовый запуск Assemble и Test в студенческом шаблоне. Спросите: «Что теперь подтверждает зелёный CI? Какие сценарии ещё не проверены?»

## 6. Передача базы и самостоятельная работа — 5–10 минут

Откройте студенческий шаблон. Покажите Use this template → Create a new repository, создание своей копии, клонирование и открытие в IDEA. В адресе клонирования каждый использует свой username GitHub.

Все получают рабочую базу с двумя тестами, независимо от того, успели ли повторить демонстрацию.

- Маршрут A: новые требования к имени, три новых теста, исправление.
- Маршрут B: ревью `canSendMessage`, свои тесты, исправление. Покажите условие и пять закрытых подсказок, но не решение.

Объясните порядок: открыть одну подсказку, применить её и запустить тесты, затем переходить к следующей. Подсказки можно использовать и для проверки уже готового решения.

Обратная связь во время самостоятельной работы: попросите назвать аргументы, ожидаемый результат, фактический результат и прочитать сообщение теста. При затруднениях направьте к следующей подсказке.

## После занятия

Опубликуйте общий разбор из `teacher-solutions.md`, когда студенты попробуют решить задачу. Сейчас разбор хранится только в комплекте преподавателя и не включён в студенческий репозиторий или статью Academy.

Индивидуальная проверка каждого репозитория не требуется. Цель самопроверки — осмысленные тесты и объяснение найденных ошибок, а не совпадение кода с эталоном.
